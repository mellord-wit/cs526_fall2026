This is the recursion tree for fib(5). The orange boxes are fib(3), computed twice. The blue boxes are fib(2), computed three times. Point at the left subtree under fib(4): the whole fib(3) subtree on the right is an exact copy of work we already did on the left. That gap is what dynamic programming removes.

The key idea

Two properties make a DP problem

Overlapping subproblems

The naive recursion solves the same smaller problem many times.

Fix: solve each one once and store the answer.

Optimal substructure

The best answer is built from the best answers to smaller problems.

Result: we can write a recurrence.

Dynamic programming = recursion + a table of remembered answers.

CS 526 · Dynamic Programming · 5

These are the two properties to check for. Overlapping subproblems: without it, caching gains nothing. Merge sort, for example, splits into halves that never repeat, so it is divide and conquer, not DP. Optimal substructure: the best solution contains best solutions to its subproblems. Shortest paths have it: the best route from A to C through B uses the best route from A to B. Longest simple path does not, which is why it has no easy DP. The name “dynamic programming” is historical: Richard Bellman chose it in the 1950s. “Programming” meant planning with a table, not writing code.

Approach 1 · Top-down

Memoization: recurse, then cache

def fib(n, memo=None):
    if memo is None:
        memo = {} # new dict for each top call
    if n in memo: # solved already?
        return memo[n]
    if n <= 1: # base cases
        return n
    memo[n] = fib(n - 1, memo) + fib(n - 2, memo)
    return memo[n]

O(n) time

Each fib(k) is computed once. fib(40) now takes 79 calls.

O(n) space

The memo dict plus the call stack.

Python shortcut

Put @functools.lru_cache on the plain recursive version.

CS 526 · Dynamic Programming · 6

Memoization keeps the recursive code and adds a lookup table. Before doing any work we check the table; after doing the work we store the result. The recursion still happens top-down, starting from n, but each subproblem is solved only once. Count: fib(40) makes 79 calls instead of 331 million (each of fib(2)..fib(40) does real work once, plus the cache hits). Point out memo=None: writing memo={} as a default argument is a classic Python trap, because that one dict is shared between all calls of the function. It happens to work here, but it is a bug waiting to happen in other problems. Mention that HW5’s lais1.py already used this pattern: the longest_lengths_of_a and longest_lengths_of_b lists start at −1 and act as memo tables. The functools.lru_cache decorator does the same caching for you on any function whose arguments are hashable.

Approach 2 · Bottom-up

Tabulation: fill a table in order

def fib(n):
    if n <= 1:
        return n
    table = [0] * (n + 1) # table[i] = fib(i)
    table[1] = 1
    for i in range(2, n + 1): # small to large
        table[i] = table[i - 1] + table[i - 2]
    return table[n]

No recursion

A loop fills the table from the base cases up.

Same O(n) time

No call overhead, no recursion limit.

O(1) space is possible

Each cell needs only the last two, so keep two variables.

CS 526 · Dynamic Programming · 7

Tabulation turns the recursion inside out. We decide in advance which order to solve subproblems in, smallest first, so that whenever we need table[i − 1] and table[i − 2] they are already filled. Draw the table on the board: 0, 1, 1, 2, 3, 5, 8, 13 filling left to right. Because each cell only looks back two places, we can throw the rest of the table away. The example file has fib_two_vars: prev, curr = 0, 1; then loop n times doing prev, curr = curr, prev + curr; return prev. That is O(n) time and O(1) space. Saving space this way is common in bottom-up DP: if row i only needs row i − 1, keep two rows.

Choosing a style

Top-down vs. bottom-up

Top-down (memoization)Bottom-up (tabulation)
How you write itRecursion plus a cacheLoops that fill a table
Order of workSet by the recursionYou choose it explicitly
SolvesOnly subproblems it needsEvery cell in the table
OverheadCalls; depth limit near 1000None; easy to cut space

Both give the same answers and the same big-O time. A good habit: write top-down first to get it right, then convert to bottom-up.

CS 526 · Dynamic Programming · 8

Neither style is “the real DP”; both are. Top-down is often easier to get right because it mirrors the recurrence, and it skips states that are never reached. Bottom-up avoids Python’s default recursion limit of 1000 frames (sys.getrecursionlimit()), so memoized fib(5000) raises RecursionError while the loop version is fine. Bottom-up also makes space savings visible. Suggest the workflow: recurrence first, memoize to test it, then convert to a table if speed or depth matters. That is about 20 minutes in; next is the recipe.

The recipe

Five steps for any DP problem

1

Define the subproblem

Say in words what dp[i] or dp[i][j] means.

2

Write the recurrence

Express one subproblem using smaller ones.

3

Set the base cases

Answer the smallest inputs directly.

4

Pick an order

Fill cells so every dependency is ready first.

5

Read the answer

Find it in the table, then trace back the choices.

Step 1 is the hard part. If you can say what dp[i] means in one sentence, the rest usually follows.

CS 526 · Dynamic Programming · 9

Apply the recipe to Fibonacci out loud so students see it once on an easy problem. 1: table[i] is the i-th Fibonacci number. 2: table[i] = table[i − 1] + table[i − 2]. 3: table[0] = 0, table[1] = 1. 4: increasing i. 5: the answer is table[n]. Stress step 1. Most wrong DP solutions come from a vague subproblem. Students should write the meaning of the table as a comment in their code, the way the tabulation slide did. We will use these five steps, labelled, on each of the next three examples.

CS 526 · Dynamic Programming · 10

About 23 minutes in. Pose the problem before showing the answers and ask the class for the fewest coins. Many will say 3 (4 + 1 + 1) because that is what greedy does, and greedy works for US coins (1, 5, 10, 25). With 1, 3, 4 it fails: 3 + 3 uses only 2 coins. This is the point of the example: when a greedy choice can be wrong, we need to consider every choice, and DP makes that affordable. The DP idea: whatever the best solution is, it has some last coin c. Remove it, and what remains must be a best solution for amount − c. That is optimal substructure.

CS 526 · Dynamic Programming · 11

Walk the recipe. 1, subproblem: dp[a] is the fewest coins making exactly a. 2, recurrence: try each coin c as the last coin; the rest costs dp[a − c]; take the minimum and add 1. 3, base case: dp[0] = 0, and any amount we cannot make stays at infinity. 4, order: a from 1 up to the target, because dp[a] only looks at smaller amounts. 5, answer: dp[6] = 2. Fill the table live on the board, one column at a time, asking students for each value. The “last coin” row records which coin won, and it lets us rebuild the solution: from 6 take a 3, go to dp[3], take a 3, reach 0. So the coins are 3 + 3.

Example 1 · Coin change

Coin change in Python

def min_coins(coins, amount):
    INF = float("inf")
    dp = [0] + [INF] * amount # dp[0] = 0
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a and dp[a - c] + 1 < dp[a]:
                dp[a] = dp[a - c] + 1
    return dp[amount] if dp[amount] != INF else -1

min_coins([1, 3, 4], 6) # 2

Time O(A · k)

A amounts, each tries k coins.

Space O(A)

One list of length A + 1.

Impossible amounts

Stay at infinity, so we return −1.

CS 526 · Dynamic Programming · 12

The code is the recurrence almost word for word. The outer loop is the evaluation order; the inner loop tries every last coin. Using infinity for “not reachable yet” means we never need a special case: infinity + 1 is still infinity in Python floats. Example: coins [5, 10] and amount 3 returns −1. Quick variation to ask: how would you count the number of ways to make the amount instead of the fewest coins? Answer: replace min with a sum, set ways[0] = 1, and loop over coins in the outer loop so that each combination is counted once and not once per ordering. That is about 32 minutes in.

Example 2 · 0/1 knapsack

Pack the most value into capacity 7

ItemWeightValue
A11
B34

D57

Each item is taken whole or left behind (0 or 1 of it).

Subproblem: K[i][c] = the best value using only the first i items with capacity c.

skip = K[i-1][c]
take = K[i-1][c - w[i]] + v[i] # if w[i] <= c
K[i][c] = max(skip, take)
K[0][c] = 0 # no items, no value

CS 526 · Dynamic Programming · 13

About 32 minutes in. Ask first: which items would you pack? Students often grab D, the most valuable item (7), then can only add A for a total of 8. The best is B + C: weight exactly 7, value 9. Greedy by value per weight also fails here: A is 1.0, B 1.33, C 1.25, D 1.4, so greedy takes D and then A, for 8. Now the recurrence. Consider item i last. Either we skip it, and the answer is the best with the first i − 1 items and the same capacity, or we take it, gaining v[i] and losing w[i] of capacity. Two choices, take the better one. The table now has two dimensions because the subproblem needs two numbers to describe it: how many items we may use, and how much room is left.

CS 526 · Dynamic Programming · 14

Fill this on the board one row at a time. Row “none” is all zeros: the base case. Row +A: once capacity is at least 1, we can take A for value 1. Row +B: at capacity 3 we take B for 4; at 4 we take B and A for 5. The interesting cell is row +C, capacity 7, in orange. Skipping C leaves the row-B value at capacity 7, which is 5. Taking C uses 4 of the 7 units, leaving capacity 3, where row B says 4; plus C’s value 5 gives 9. The blue cells are the two values that cell compares. The last row adds D, but at capacity 7 taking D gives K[C][2] + 7 = 8, which is worse than 9, so the answer stays 9. Each cell looks only at the row above, so row order is a valid evaluation order. Size: (n + 1) × (C + 1) cells, each O(1), so O(n·C) time. Note that this is pseudo-polynomial: it depends on the numeric capacity, not just the number of items.

Example 2 · 0/1 knapsack

Knapsack in Python

def knapsack(weights, values, cap):
    n = len(weights)
    K = [[0] * (cap + 1) for _ in range(n + 1)]
    for i in range(1, n + 1):
        w, v = weights[i - 1], values[i - 1]
        for c in range(cap + 1):
            K[i][c] = K[i - 1][c] # skip item i
            if w <= c: # or take it
                take = K[i - 1][c - w] + v
                K[i][c] = max(K[i][c], take)
    return K[n][cap]

knapsack([1, 3, 4, 5], [1, 4, 5, 7], 7) # 9

Time O(n · C)

One O(1) step per cell.

Space O(n · C)

Keep the whole table to recover the items.

Watch the index

Row i uses weights[i − 1].

CS 526 · Dynamic Programming · 15

Point out the off-by-one: the table has n + 1 rows so that row 0 can be the “no items” base case, which means row i describes item i − 1 in the Python lists. Ask: why must the inner loop read from row i − 1 and not row i? Because reading row i would let us take the same item twice. That other version is the unbounded knapsack, where every item can be reused, and it is the same code with K[i][c − w] instead of K[i − 1][c − w]. If you only need the value, you can keep a single 1-D list and loop c downward from cap to w; looping downward is what keeps each item to one use. To list the chosen items, keep the full table: next slide.

Example 2 · Step 5

Tracing back which items we took

def chosen_items(K, weights, cap):
    items, c = [], cap
    for i in range(len(weights), 0, -1):
        if K[i][c] != K[i - 1][c]: # changed
            items.append(i - 1) # so taken
            c -= weights[i - 1]
    return items[::-1]

D: 9 = 9 above, so skip

C: 9 ≠ 5, take; c = 7 − 4 = 3

B: 4 ≠ 1, take; c = 3 − 3 = 0

A: 0 = 0, skip

Result: B + C, weight 7, value 9

CS 526 · Dynamic Programming · 16

The table stores values, not decisions, but the decisions can be recovered. Start at the bottom-right cell. If K[i][c] is the same as the cell straight above it, item i was not needed, so move up. If it is different, item i must have been taken, so record it, subtract its weight from c, and move up. Walk it on the table from the previous slide: D is skipped, C is taken, capacity drops to 3, B is taken, capacity drops to 0, A is skipped. This is step 5 of the recipe, and the same trick works for coin change (the last-coin row) and for LCS next. About 44 minutes in.

LCS = B C B, length 3. A subsequence keeps the order but may skip letters.

Subproblem: L[i][j] = LCS length of the first i letters of X and the first j letters of Y.

# i = 0 or j = 0:
L[i][j] = 0

CS 526 · Dynamic Programming · 17

About 44 minutes in. Define subsequence versus substring: a substring must be contiguous, a subsequence only needs to keep the order. B C B is a subsequence of BACDB (skip A and D) and of BDCB (skip D). B D B also works, which shows the LCS is not always unique, though its length is. Applications: diff and git compare files line by line with LCS, and DNA sequence alignment uses close relatives of it. The recurrence comes from looking at the last letters. If they match, that letter can end the LCS, so we take 1 plus the LCS of both prefixes without it. If they do not match, at least one of the two last letters is not in the LCS, so we drop one or the other and keep the better answer.

CS 526 · Dynamic Programming · 18

Rows are letters of X = BACDB, columns are letters of Y = BDCB, with an empty-prefix row and column of zeros as the base case. Fill row by row, left to right: each cell needs the cell above, the cell to the left and the diagonal, all already filled. Do two cells together with the class. Row C, column C: the letters match, so take the diagonal (row A, column D = 1) plus 1 = 2. Row D, column C: no match, so take the larger of above (2) and left (2) = 2. The answer is the bottom-right cell, 3. Trace back: at a match, record the letter and move diagonally; otherwise move toward the larger neighbour (on a tie, pick one consistently). The bold cells are the matches on the path, which spell B, C, B.

Example 3 · Longest common subsequence

LCS in Python

def lcs_length(x, y):
    m, n = len(x), len(y)
    L = [[0] * (n + 1) for _ in range(m + 1)]
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if x[i - 1] == y[j - 1]:
                L[i][j] = L[i - 1][j - 1] + 1
            else:
                L[i][j] = max(L[i - 1][j], L[i][j - 1])
    return L[m][n]

lcs_length("BACDB", "BDCB") # 3

Time O(m · n)

One O(1) step per cell.

Space O(m · n)

Two rows suffice for the length alone.

Brute force

x has 2^m subsequences: exponential.

CS 526 · Dynamic Programming · 19

Same shape as knapsack: a table one bigger than the inputs in each dimension, a double loop, and an off-by-one where row i means the letter x[i − 1]. Contrast with brute force: a string of length m has 2^m subsequences, so checking each one against y is exponential, while the table is m·n. For two 1,000-character strings that is one million cells, instant. The example file has lcs_string, which does the trace back and returns the actual subsequence. About 53 minutes in.

Debugging DP

Five common bugs and their fixes

BugFix
Default memo={} shared by every callUse memo=None, or @lru_cache
Off-by-one: table is size n, not n + 1Leave row 0 for the base case
Cell read before it is filledCheck each cell’s dependencies come first
RecursionError on large inputsSwitch to bottom-up loops
Assuming greedy is optimalLook for a counterexample, like coins [1, 3, 4]

Test on tiny inputs and compare with the brute-force recursion before trusting the table.

CS 526 · Dynamic Programming · 21

These five come up in almost every DP assignment. The mutable default argument is Python-specific: def f(n, memo={}) creates one dict when the function is defined, and every later call shares it. Off-by-one errors come from mixing up “first i items” (table index) with “item i” (list index). The dependency bug shows up as answers that are too small, because the code reads zeros that have not been computed yet. The best debugging habit is the last line: keep the slow recursive version and compare outputs for every small input. The example file does exactly this in its self-test.

Extension · Several indices

Choosing the state

“If I stopped halfway, what would I have to write down so someone else could finish the job optimally?”

Knapsack: (i, c)

Only the items left and the room left matter, not which items were chosen.

Add a volume limit: (i, w, v)

Now the volume left matters too, so it becomes a third index.

Missing a dimension? Two histories reach the same state but need different decisions from there on.

CS 526 · Dynamic Programming · 26

This question is the most useful tool for step 1 of the recipe when there are several constraints. Each independent item on the list you would write down becomes one dimension. Work the knapsack example: after deciding about the first i items, the best way to finish depends only on i and the capacity left. Adding a volume limit means the remaining volume also matters. The test at the bottom catches a state that is too small: if two different histories land in the same cell but the best future moves differ between them, the cell is mixing two situations and the state needs another piece of information.

Each dimension multiplies the table by its range. Add only the ones you need.

Fill order

Indices only decrease (LCS, knapsack): nested increasing loops, in any nesting.

Intervals dp[i][j]: loop over the length first.

Floyd-Warshall: the k loop must be outermost.

Memoization: the recursion finds the order for you.

CS 526 · Dynamic Programming · 27

Two practical questions for any multidimensional table. Cost: the number of states is the product of the ranges of the indices, and each new dimension multiplies it. This is the curse of dimensionality; 100 million cells of Python lists is close to a gigabyte. Order: every cell may read only cells that are already filled, so find an order in which every arrow of the recurrence points backward. When every dependency has smaller indices, as in LCS and knapsack, any nesting of increasing loops works. Interval DP depends on shorter intervals, so loop over the length. In Floyd-Warshall, k means “may use cities 0..k as stops”, so it has to be the outer loop. With many dimensions, a memoized version is often the easiest correct first draft.

LCS of three strings

Subproblem: L[i][j][k] = LCS length of a[:i], b[:j] and c[:k].

# any index is 0:
L[i][j][k] = 0
# all three last letters equal:
L[i][j][k] = L[i-1][j-1][k-1] + 1
# otherwise drop one last letter:
L[i][j][k] = max(L[i-1][j][k],

Why not run 2-string LCS twice?

a = "AB"
b = "BA"
c = "B"

LCS(a, b) may return “A”, and “A” shares nothing with c: 0.

True answer: 1 (“B”). The third index keeps every option open.

CS 526 · Dynamic Programming · 28

This is the gentlest 3-D example because the recurrence is the 2-D one with one more term. If all three last letters match, that letter can end the common subsequence. Otherwise at least one of the three last letters is not in it, so drop each in turn and keep the best. Work the counterexample on the board: the LCS of AB and BA has length 1 and can be either A or B. A program that happens to pick A then finds nothing in common with c = B, but the true three-way answer is 1. Solving in two passes throws away information that the third index keeps.

Extension · 3-D example

Three-string LCS in Python

def lcs3(a, b, c):
    p, q, r = len(a), len(b), len(c)
    L = [[[0] * (r + 1) for _ in range(q + 1)]
         for _ in range(p + 1)]
    for i in range(1, p + 1):
        for j in range(1, q + 1):
            for k in range(1, r + 1):
                if a[i - 1] == b[j - 1] == c[k - 1]:
                    L[i][j][k] = L[i - 1][j - 1][k - 1] + 1
                else:
                    L[i][j][k] = max(L[i - 1][j][k],
                                     L[i][j - 1][k],
                                     L[i][j][k - 1])
    return L[p][q][r]

Time O(p · q · r)

One O(1) step per cell.

Example

BACDB, BDCB, BCDB: 150 cells, answer 3 (BCB or BDB).

Top-down

@lru_cache on L(i, j, k) caches by the tuple of indices.

Extension · Saving space

One row: the loop direction matters

0/1 knapsack: loop downward

def knapsack_1d(weights, values, cap):
    best = [0] * (cap + 1)
    for w, v in zip(weights, values):
        for c in range(cap, w - 1, -1):
            best[c] = max(best[c], best[c - w] + v)
    return best[cap]

knapsack_1d([2], [3], 4) is 3: the item once.

Unbounded: loop upward

def knapsack_unbounded(weights, values, cap):
    best = [0] * (cap + 1)
    for w, v in zip(weights, values):
        for c in range(w, cap + 1):
            best[c] = max(best[c], best[c - w] + v)
    return best[cap]

knapsack_unbounded([2], [3], 4) is 6: the item twice.

Same body, opposite direction, different problem. If a cell reads to its left in the old row, loop from right to left.

CS 526 · Dynamic Programming · 32

This is the slide to slow down on. In 0/1 knapsack, cell c of the new row reads cell c − w of the OLD row. Looping c downward means that when we read best[c − w] it has not been overwritten for this item yet, so it still holds the old row’s value. Loop upward and best[c − w] may already include this item, so the item gets counted again; that is exactly the unbounded knapsack, where each item may be reused. Trace the tiny example on the board: one item of weight 2 and value 3, capacity 4. Downward: best[4] reads the old best[2] = 0, giving 3. Upward: best[2] becomes 3 first, then best[4] reads it and becomes 6. The rule to remember is the last line: draw the arrows, and loop against them.

Extension · Saving space

LCS in one row: save the diagonal

def lcs_one_row(x, y):
    row = [0] * (len(y) + 1)
    for i in range(1, len(x) + 1):
        diag = 0 # L[i-1][j-1]
        for j in range(1, len(y) + 1):
            saved = row[j] # L[i-1][j], about to change
            if x[i - 1] == y[j - 1]:
                row[j] = diag + 1
            else:
                row[j] = max(row[j], row[j - 1])
            diag = saved
    return row[len(y)]

The problem

The diagonal L[i-1][j-1] was overwritten one step ago.

The fix

Save it in diag before overwriting, one cell at a time.

Same trick in 3-D

Floyd-Warshall updates one 2-D table in place.

CS 526 · Dynamic Programming · 33

LCS reads three neighbours: above, left and the diagonal. In a single row, “above” is the value still sitting in row[j] before we overwrite it, and “left” is row[j − 1], already updated for this row, which is what we want. Only the diagonal is lost, because it was row[j − 1] before the previous step overwrote it. So we carry it along in diag. Another useful move: put the shorter string on the row axis, so the space is O(min(m, n)); for strings of length 1,000,000 and 100 that is a row of 101 cells. For three strings, lcs3 needs only two 2-D layers, O(q·r) space. Floyd-Warshall goes further and keeps a single 2-D table updated in place. That is safe because pass k never changes row k or column k: d[i][k] + d[k][k] is just d[i][k], since d[k][k] = 0.

Extension · Saving space

Getting the choices back

Rolling rows lose step 5, the trace back. Three ways to recover it:

Decision bytes

Keep values in one row, and one byte per cell (taken or not) in a bytearray.

About 8 times smaller than all the values

Checkpoints

Save every s-th row. To trace back, recompute the rows between two checkpoints.

O(sqrt(m) · n) space, about 2× time

Hirschberg

Find where the answer crosses the middle row, split there, and recurse on both halves.

An actual LCS in O(min(m, n)) space

CS 526 · Dynamic Programming · 34

A rolled table gives the value but not the choices behind it. Decision bytes: knapsack_with_items in the text file keeps the values in a single row and records, in a bytearray, whether each item improved each capacity. A list slot holds an 8-byte reference, so the decisions are about 8 times smaller than the full value table, and the trace back walks them from the last item to the first. Checkpoints: store every s-th row during the forward pass; with s about the square root of the number of rows, the memory is O(sqrt(m)·n) and the extra time roughly doubles the work. Hirschberg’s algorithm, for LCS and edit distance: compute the middle row from the top and again from the bottom on the reversed strings, find the column where the best answer crosses the middle, and solve the two halves the same way. It gives an actual LCS in O(m·n) time and linear space, which is why it is used to align very long DNA sequences.

Extension · Complex constraints

Two levers for hard rules

At most k of something · never two in a row · a cooldown · a capacity of a billion · negative numbers

A. Tweak the state

Make the state record what the rule depends on, or reshape it so the table stays small.

B. Speed up transitions

Keep the same states, and make the work for each one cheaper.

cost = (number of states) × (work per state)

CS 526 · Dynamic Programming · 35

About 30 minutes into the extension. Real problems arrive with extra rules. Read the list at the top and ask students which lever each one needs; most need lever A. Tie it to the formula at the bottom: lever A changes the first factor, either by adding information the rule needs or by reshaping the state so there are fewer states; lever B attacks the second factor, the work per state. Walk the rows. Counter: knapsack with at most m items keeps best[j][c] for j items, looping both j and c downward so each item is used once; with the lecture items and m = 1 the answer drops to 7 (D alone), with m = 2 it is 9 (B and C). Extension · Lever A

Huge capacity? Index by value

New subproblem: least[t] = the smallest weight that reaches a total value of exactly t.

def knapsack_by_value(weights, values, cap):
    INF = float("inf")
    total = sum(values)
    least = [0] + [INF] * total
    for w, v in zip(weights, values):
        for t in range(total, v - 1, -1):
            least[t] = min(least[t], least[t - v] + w)
    return max(t for t in range(total + 1) if least[t] <= cap)

Capacity 2 billion

Values 3 and 5 make a table of only 9 cells. Answer: 5.

Time

O(n · sum of values), not O(n · capacity).

Lecture items

Still 9, as on slide 14.

CS 526 · Dynamic Programming · 37

When one index has a huge range, look for another quantity with a small range and make it the index instead. A knapsack with capacity two billion cannot have a capacity index. But if the values are small, swap the roles: the index is the total value, and the stored number is the least weight that achieves it. The answer is the largest value whose least weight fits. The example call in the text file is knapsack_by_value([10**9, 2 * 10**9], [3, 5], 2 * 10**9): the two items together weigh three billion, which is too much, so the best is the second item alone, value 5. The table has sum(values) + 1 = 9 cells. The loop still runs downward, for the same reason as slide 32: each item is used once.

A mode index for “not twice in a row”

Paint houses: neighbors must differ in color. State = (house, its color).

def paint_houses(cost):
    prev = [0] * len(cost[0]) # prev[c]: cheapest, ends in c
    for row in cost:
        curr = []
        for c in range(len(row)):
            others = [prev[d] for d in range(len(row)) if d != c]
            curr.append(row[c] + min(others))
        prev = curr
    return min(prev)

Example

Costs [[17, 2, 17], [16, 16, 5], [14, 3, 19]] give 10: 2 + 5 + 3.

The pattern

The example picks colors 1, 2, 1 counting from 0, costing 2 + 5 + 3 = 10. The general habit is to draw the rule as a small state machine. CS 526 · Dynamic Programming · 39

Lever B keeps the states and cuts the work per state. If dp[i] looks back at k earlier cells, the total is O(n·k), and many of those inner loops are a sum, minimum or maximum over a range. Prefix sums: climbing 1 to k stairs at a time, ways[i] is the sum of the previous k values; with prefix[i] = ways[0] + … + ways[i − 1], that sum is prefix[i] − prefix[i − k], so climb_ways(10, 3) = 274 takes O(n) for any k. Running best: for buying a stock once and selling later, keep the lowest price so far instead of rescanning every earlier day; best_profit([7, 1, 5, 3, 6, 4]) is 5. Bundles: an item available 10 times becomes bundles of 1, 2, 4 and 3, four 0/1 items that can make any count from 0 to 10. The next two slides show the deque and the binary search. The last row of names is for recognition only: the convex hull trick handles transitions that are a minimum over lines; Knuth’s optimization speeds up interval DPs like the optimal binary search tree from O(n³) to O(n²); the divide-and-conquer optimization applies when the best split point never decreases.

Extension · Lever B

Sliding-window max with a deque

from collections import deque

def max_jump_score(nums, k):
    dp = [0] * len(nums)
    dp[0] = nums[0]
    window = deque([0]) # indices, dp decreasing
    for i in range(1, len(nums)):
        while window[0] < i - k:
            window.popleft() # out of the window
        dp[i] = nums[i] + dp[window[0]]
        while window and dp[window[-1]] <= dp[i]:
            window.pop() # never the max again
        window.append(i)
    return dp[-1]

The problem

Jump 1 to k squares at a time; maximize the sum you land on.

O(n), not O(n · k)

Each index enters and leaves the deque once.

Example

[1, −1, −2, 4, −7, 3], k = 2: 7 (1 − 1 + 4 + 3)

CS 526 · Dynamic Programming · 40

The recurrence is dp[i] = nums[i] + the maximum of dp[i − k] through dp[i − 1]. Recomputing that maximum costs k per cell. The deque holds indices whose dp values decrease from front to back, so the front is always the maximum of the window. Two rules keep it that way. First, drop indices from the front once they are more than k back. Second, before adding i, pop every index from the back whose dp value is no better than dp[i]: it is older and no larger, so it can never be the maximum again. Each index is pushed once and popped at most once, so the whole loop is O(n). For a sliding minimum, flip the comparison.

Extension · Lever B

LIS in O(n log n) with bisect

New state: tails[L] = the smallest value that can end an increasing subsequence of length L + 1. It is always sorted.

from bisect import bisect_left

def lis_length(nums):
    tails = []
    for x in nums:
        pos = bisect_left(tails, x)
        if pos == len(tails):
            tails.append(x)
        else:
            tails[pos] = x
    return len(tails)

The practice problem from slide 22 solved the slow way is O(n²): dp[i] = 1 + the best dp[j] over earlier, smaller values. This version uses both levers. Lever A changes the state: the index is now a length and the stored value is the smallest possible last element, a swap of index and value as on slide 37. Extension · Putting it together

A checklist for constrained problems

1

Write the plain recurrence. Ignore the hard rule at first.

2

For each rule: forbids states → impossible value; counts → counter; previous step → mode; a set → bitmask.

3

Count the states. An index with a huge range → swap index and value, or drop variables you can compute.

4

Check each inner loop: range sum → prefix sums; sliding max or min → deque; sorted list → binary search; all earlier → running best.

5

Only then shrink the space, and test against the full-table version.

CS 526 · Dynamic Programming · 42

This checklist combines the extension into one procedure; steps 2 and 3 are lever A and step 4 is lever B. Try it live on a problem students have not seen, for example “longest path in a grid that turns at most k times”: the plain recurrence moves right or down; the turn limit is a counter; whether the last move was right or down is a mode; so the state is (row, column, turns used, last direction). Step 5 is a reminder that space comes last: shrink only a version that is already correct, and keep the slow version to compare against.
